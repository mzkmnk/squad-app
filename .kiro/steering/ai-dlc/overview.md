# AI-DLC ワークフロー概要

本ドキュメントは AWS が提唱する AI-DLC（AI-Driven Development Life Cycle）の公式ワークフローに基づく、
本プロジェクト向けのカスタムガイドラインである。

参照元: [awslabs/aidlc-workflows](https://github.com/awslabs/aidlc-workflows)

## 基本原則

1. **適応的ワークフロー**: ワークフローは作業に適応する。作業がワークフローに合わせるのではない
2. **Human-in-the-Loop**: 全ての重要な決定にはユーザーの明示的な承認が必要
3. **計画優先**: コード生成に飛びつかず、まず計画を立て承認を得る
4. **監査可能性**: 全ての操作・承認を `docs/aidlc/{feature_name}/audit.md` に記録する
5. **逸脱禁止**: 承認された計画からの逸脱は許可されない

## 3フェーズ構成

### 🔵 INCEPTION フェーズ — WHAT と WHY を決める

| ステージ              | 実行条件                 | 目的                                 |
| --------------------- | ------------------------ | ------------------------------------ |
| Workspace Detection   | 常に実行                 | greenfield/brownfield 判定           |
| Reverse Engineering   | brownfield のみ          | 既存コードの分析                     |
| Requirements Analysis | 常に実行（深度は適応的） | 要件の収集・検証                     |
| User Stories          | 条件付き                 | ユーザーストーリーとペルソナの作成   |
| Workflow Planning     | 常に実行                 | 実行するステージの決定               |
| Application Design    | 条件付き                 | コンポーネント・サービス層の概念設計 |
| Units Generation      | 条件付き                 | Unit of Work への分解                |

### 🟢 CONSTRUCTION フェーズ — HOW を決めて実装する

| ステージ              | 実行条件              | 目的                                           |
| --------------------- | --------------------- | ---------------------------------------------- |
| Functional Design     | 条件付き（Unit 単位） | ビジネスロジックの詳細設計                     |
| NFR Requirements      | 条件付き（Unit 単位） | 非機能要件の評価                               |
| NFR Design            | 条件付き（Unit 単位） | NFR パターンの設計                             |
| Infrastructure Design | 条件付き（Unit 単位） | インフラ設計（本プロジェクトでは通常スキップ） |
| Code Generation       | 常に実行（Unit 単位） | Planning → Generation の2パート                |
| Build and Test        | 常に実行              | ビルド・テスト手順の策定                       |

### 🟡 OPERATIONS フェーズ — 将来拡張用プレースホルダー

## 用語定義

| 用語              | 定義                                                                                                                           |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Phase（フェーズ） | 3つの高レベルライフサイクル区分（Inception / Construction / Operations）                                                       |
| Stage（ステージ） | フェーズ内の個別ワークフロー活動                                                                                               |
| Unit of Work      | ストーリーの論理的グルーピング。マイクロサービスなら独立デプロイ可能なサービス、モノリスならアプリ全体（内部に Module を持つ） |
| Service           | 独立デプロイ可能なコンポーネント（マイクロサービスアーキテクチャ）                                                             |
| Module            | サービスまたはモノリス内の論理的な機能グルーピング。独立デプロイ不可                                                           |
| Component         | サービスまたはモジュール内の再利用可能な構成要素（クラス、関数、パッケージ）                                                   |
| Planning          | 質問とチェックボックスを含む計画の作成                                                                                         |
| Generation        | 承認された計画に基づく成果物の生成                                                                                             |

## 適応的深度（Adaptive Depth）

ステージが実行される場合、定義された全成果物が作成される。
「深度」とは成果物内の詳細レベルを指し、問題の複雑さに応じて適応する。

- **Minimal**: 単純で明確なリクエスト。簡潔な成果物
- **Standard**: 通常の複雑さ。標準的な成果物
- **Comprehensive**: 複雑・高リスク。詳細な成果物とトレーサビリティ

深度を決定する要因:

1. リクエストの明確さ
2. 問題の複雑さ
3. スコープ（単一ファイル〜システム全体）
4. リスクレベル
5. 既存コンテキスト（greenfield vs brownfield）

## 質問フォーマット

ユーザーへの質問は以下のルールに従う:

- 選択肢は A, B, C, D 等でラベル付け
- 常に「X) その他（[Answer]: タグの後に記述してください）」を含める
- 選択肢は相互排他的で重複しないこと
- `[Answer]:` タグ形式でファイルに埋め込み、ユーザーがファイル内で回答する
- 全ての回答を曖昧さ分析し、必要に応じてフォローアップ質問を追加

## チェックポイント承認

各ステージの完了時に以下の形式で承認を求める:

```markdown
> **📋 REVIEW REQUIRED:**
> [成果物のパス] を確認してください

> **🚀 WHAT'S NEXT?**
>
> 🔧 **変更を依頼** - 修正が必要な場合
> ✅ **承認して次へ** - [次のステージ名] に進む
```

ユーザーの明示的な承認なしに次のステージに進んではならない。
