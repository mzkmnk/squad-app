# Requirement Verification Questions — workspace-edit

## 機能スコープ

### Q1: 編集対象の範囲

Workspace の「編集」として、以下のどの操作をスコープに含めますか？

- (a) エントリの追加（リポジトリ × ブランチの組み合わせを追加）
- (b) エントリの削除（既存のリポジトリ × ブランチを除去）
- (c) エントリのブランチ変更（同一リポジトリで別ブランチに切り替え）
- (d) Workspace の表示名（displayName）の変更
- (e) 上記すべて

`[Answer]:`

- a
- b

c についてですが、これはたとえばworktreeでブランチを作成した場合、このworktreeには持ってこれないよね？持ってくるとしたら現在の実装を見る感じ**remote**の最新からチェックアウトするような形だよね？
d はどのことを言っている？

### Q2: エントリ追加時の新規ブランチ作成

エントリ追加時に、既存ブランチの選択だけでなく、新規ブランチの作成（workspace:create と同様の sourceBranch 指定）もサポートしますか？

`[Answer]:`
はい、どちらもサポートします。ただUIですが、既存ブランチ選択も、起点ブランチの作成となっていると思う。

### Q3: ブランチ変更の実現方法

エントリのブランチ変更をスコープに含める場合、実装方法はどちらを想定していますか？

- (a) 既存 Worktree を削除 → 新しいブランチで Worktree を再作成（シンプルだがローカル変更は失われる）
- (b) Worktree 内で `git checkout` / `git switch`（ローカル変更を保持できるが複雑）

`[Answer]:` Q1で懸念していることなのでQ1がどうなるか決まったら回答します。

## ユーザーインタラクション

### Q4: 編集 UI の形式

編集画面はどのような形式を想定していますか？

- (a) 一覧画面のカードクリックで編集ダイアログを開く（作成ダイアログと同様の形式）
- (b) 専用の編集ページに遷移する
- (c) カード上でインライン編集する
- (d) その他

`[Answer]:`
これは要相談したい。

### Q5: 編集のトリガー

編集操作へのアクセス方法はどれを想定していますか？

- (a) カードに「編集」ボタンを追加（削除ボタンの隣）
- (b) カードクリックの動作を「IDE で開く」から「編集ダイアログを開く」に変更
- (c) カードの右クリックメニュー / コンテキストメニュー
- (d) その他

`[Answer]:`
そうですね、削除ボタンの左隣に編集ようなアイコンを置きたいと考えています。

## エッジケース・制約

### Q6: 最後のエントリの削除

Workspace から全てのエントリを削除した場合（エントリ数が 0 になる場合）の挙動はどうしますか？

- (a) 最低1つのエントリを必須とし、最後の1つは削除不可にする
- (b) エントリ 0 の Workspace を許可する
- (c) 全エントリ削除時は Workspace 自体の削除を提案する

`[Answer]:` cかな。

### Q7: IDE で開いている Workspace の編集

VS Code（または他の IDE）で開いている Workspace を編集した場合、`.code-workspace` ファイルの再生成で IDE 側に影響が出る可能性があります。この点について:

- (a) 特に制御しない（IDE 側が自動リロードする前提）
- (b) 編集前に警告を表示する
- (c) 初期リリースでは考慮しない

`[Answer]:` aでいいかな

### Q8: 同一リポジトリの重複エントリ

リバースエンジニアリング分析で指摘された通り、現在の Worktree ディレクトリ構造（`<workspaceName>/<repoName>`）では同一リポジトリの複数エントリは不可能です。この制約を:

- (a) そのまま維持する（同一リポジトリは1エントリのみ）
- (b) ディレクトリ構造を変更して対応する（スコープ拡大）

`[Answer]:` aで行こう。ただUIでは選択できないようにするなどの処理が必要。
